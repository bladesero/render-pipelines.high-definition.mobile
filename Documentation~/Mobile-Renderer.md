# Experimental HDRP Mobile renderer

This fork adds an independently initialized mobile backend with Forward and optional Deferred paths to HDRP 14.0.9 / Unity 2022.3. It targets Android Vulkan. It is a project-maintained extension, not official Unity HDRP mobile support. Windows D3D11/D3D12 are supported in Editor and Player; Vulkan is also available for Editor validation. Desktop Auto deferred uses stored GBuffer textures without tile-storage subpasses.

## Setup

Forward remains the default. Optional deferred uses three color targets and at most one extra RGBA8 Fresnel/Coat target. Other Lit types render through Forward; screen-space SSS is unavailable. See [Mobile deferred](Mobile-Deferred.md) for routing and attachment budgets.

1. Create **Assets > Create > Rendering > HDRP Mobile Pipeline Asset**. Alternatively select an HDRP Asset and set **Renderer Mode = Mobile**. Mobile shaders load automatically from HDRP runtime resources; no manual resource configuration is required.
2. Assign that asset in Graphics settings and the Quality levels that should use the Mobile backend. Android requires every included level to use Mobile; Windows can also use Mobile for its application. Keep a separate Desktop asset for the authoring/baking workflow. Existing assets default to Desktop.
3. Use Linear color space. For Android, use **Lightmap Encoding = High Quality**, disable Auto Graphics API and leave **Vulkan only**. For Windows, disable Auto Graphics API and select **Direct3D11**, **Direct3D12**, or both. To enable desktop deferred, select **Rendering Path = Deferred** and **Deferred Execution = Auto** (or **Sampled**); both use stored GBuffer textures, without tile storage. The GPU must support sampling, filtering and rendering RGBA16F. MSAA, XR and OpenGL ES are unsupported.
4. Run **Rendering > HDRP Mobile > Audit Loaded Scenes**. The report identifies objects, materials and Volume overrides requiring changes. Builds also audit their scene copies. Unsupported content is reported without modifying the scene; unsupported shaders draw with the error material.
5. Open and test the mobile version of the content in the Editor, then build and profile on devices. Do not infer phone performance from an Editor frame rate.

Game cameras targeting the display default to a fixed 1920×1080 internal color/depth buffer. Final composition scales to the camera's display viewport. Disable **Fixed 1080p** to use the output dimensions instead. **Render Scale** is an explicit quality control (0.5–1); no automatic resolution controller is installed. Scene View, material previews and explicit RenderTextures use their own dimensions, multiplied by Render Scale. The performance acceptance run requires scale 1 throughout.

## Shader arithmetic precision

Mobile uses explicit `mobile_half`, `mobile_half2`, `mobile_half3` and `mobile_half4` types from `MobilePrecision.hlsl` for bounded material/BRDF values, surface normals and color intermediates. These are HLSL `min16float` types, independent of the project's Shader Precision Model. Mobile ShadowCaster variants instead map these aliases to `float` types so alpha sampling/remapping/clipping also retains FP32 arithmetic. Shared Core types and Desktop HDRP shaders are unchanged.

World positions, transforms, UVs, depth/shadow projection, GBuffer octahedral encoding and interfaces, sharp GGX denominators, physical light intensity, HDR accumulation, exposure metering and the spectral thin-film fit retain FP32 range or precision. The GGX result is clamped to finite FP16 range before narrowing. `min16float` requests minimum 16-bit arithmetic; Vulkan uses relaxed-precision values, which the driver may execute at higher precision. Native FP16 instructions are not guaranteed on every GPU. See [Unity shader precision documentation](https://docs.unity.cn/Manual/SL-Use16BitPrecisionInShaders.html).

Shadow caster transforms and bias, shadow coordinates, cascade spheres and distance tests, WorldToShadow matrices, directional/local PCF accumulation, cascade blending and shadow attenuation use FP32 throughout. This removes minimum-precision rounding in the shadow path; it does not change shadow-map storage formats or eliminate other causes of temporal aliasing.

`MobilePrecisionTests` verifies that compiled Forward/Deferred DXBC contains minimum-precision operands and saves disassembly to `mobile-precision-validation` inside the disposable validation project. It also compiles Mobile Lit/Unlit alpha-tested instanced casters and directional/local shadow receivers for D3D and Android Vulkan, and checks the D3D shadow bytecode for absence of minimum-precision operands. The URP numerical oracle checks every pixel for NaN/Inf and bounds maximum error normalized by `max(1, abs(reference))` to 0.002 (approximately two FP16 epsilons); it reports the worst sample instead of stopping at the first rounded value.

## Supported content

Mobile **Normal Bias (Texels)** offsets shadow-caster vertices along the negative world-space normal, weighted by `1 - saturate(N dot L)` where L points toward the light. Each cascade converts texels to world units using `2 / (abs(projection.m00) * tileResolution)`. One cascade uses the full atlas, two to four use a 2×2 grid, and five or six use a 3×3 grid (1365-pixel tiles at 4096). Point/Spot shadows use each Light's normal bias, scaled by perspective texel width and distance to the caster. This is a caster inset, not a receiver offset.

Add **Lighting > Mobile Shadows** to a Volume Profile to override shadow enablement, distance, cascade count, first split, blend, normal bias, CSM atlas resolution, local atlas resolution, and PCF kernel width. Unchecked overrides use the Mobile pipeline asset. The first split is a fraction of shadow distance; subsequent splits divide the remaining distance evenly. Both atlas resolutions are rounded up to a power of two and capped at 4096. Local tiles resize to accommodate up to 32 visible local lights, with six contiguous faces reserved for each Point light; lights must have realtime shadows enabled. Both Forward and Deferred respect the material's Mobile Receive Shadows flag. PCF supports 1×1, 2×2, 3×3 and 4×4 kernels; comparison samples are clamped to their tile to prevent leakage.

Mobile Forward and Deferred honor a light's HDRP **Shadow Update Mode** for directional, Spot and Point shadows. Set **Update Mode** to **On Enable** (or **On Demand**) and enable **Update on Light Movement** on the light to cache its shadow atlas. A static light reuses the previous depth map; moving or rotating it, changing shadow projection settings, changing the visible shadow-light layout, or calling `RequestShadowMapRendering()` in On Demand mode redraws the atlas. Directional cascades also redraw when the camera changes their projection. Local lights share one atlas, so changing one cached light redraws all local shadow tiles; a local light set to **Every Frame** keeps the shared local atlas on the normal per-frame path. Moving shadow casters do not invalidate a cached map automatically: request a refresh when their shadows must change. Cached depth atlases are kept per camera and released with the Mobile backend.

| Area | Mobile behavior |
| --- | --- |
| Materials | HDRP/Lit IDs 0–5 and HDRP/Unlit; deferred Standard plus optional RGBA8 SpecularColor/coat, with other Lit types using Forward; no screen-space SSS or asset conversion |
| Surface | Base color, tangent-space normal, Mask Map metallic/AO/smoothness, Detail Map UV0/UV1, emission, alpha clipping, double-sided surfaces |
| Transparency | Alpha, Premultiply and Additive; sorted forward rendering, no refraction or distortion |
| Direct lighting | One directional light; up to 32 visible point/spot lights. Forward uses up to four per object; Deferred evaluates all visible local lights in volumes |
| Shadows | Main directional light: 1–6 cascades (default 6), atlas up to 4096². Point/Spot lights: shared local atlas up to 4096², six faces per Point and one tile per Spot. PCF from 1×1 to 4×4 for both atlases. Lighting / Mobile Shadows Volume overrides the asset per camera. |
| Baked lighting | Lightmaps including directional maps and Light Probe SH. HDRP Reflection Probes use a shared octahedral atlas in Forward and Deferred, with rotated box/sphere influence, blending and proxy projection. |
| Mixed lighting | Baked Indirect only; no Shadowmask, Subtractive, realtime GI or APV |
| Background | Explicit cubemap, Volume HDRI/Gradient sky, procedural approximation of Physical Sky or legacy URP skybox, solid camera clear, optional distance fog |
| Volumes | Fixed / Physical Camera / lightweight Automatic Exposure; shared desktop White Balance, Color Adjustments, Channel Mixer, Lift/Gamma/Gain, Shadows/Midtones/Highlights, Split Toning, Color Curves; all SDR Tonemapping modes; Bloom threshold/intensity/tint; camera-configured FXAA |
| Anti-aliasing | FXAA when selected on the HDRP camera; Scene View uses HDRP Scene View camera settings. No SMAA/TAA, temporal history or motion vectors |
| Cameras | Game, Scene View, material preview, explicit RenderTexture and viewport output; each camera clears its independent targets |

HDAdditionalCameraData's volume mask/anchor and clear color/sky choice are respected. Mobile creates its own lightweight default Volume using the registered HDRP default profile, without creating desktop sky managers. Exposure Control, Postprocess, Color Grading, Tonemapping, Bloom and Anti-aliasing use the shared Desktop Frame Settings. The remaining unsupported features include Shader Graph, Layered Lit, displacement, decals, terrain, water, volumetrics, screen-space lighting, VFX Graph, Custom Pass, custom post effects, camera stacking, realtime reflection cameras, planar reflections and XR.

**Draw Unsupported Materials** adds a diagnostic magenta draw for materials lacking MobileForward. This scans loaded scene renderers once per game frame with reused collections. Disable it after a clean audit when profiling/shipping validated content; the benchmark asset disables it. Diagnostic draws are frustum/depth tested but do not reproduce native LOD/occlusion selection for unsupported content. Persistent objects are included when their scene is visited by a camera. This diagnostic is not a fallback implementation of the unsupported material's effect.

The material property buffer uses the existing Lit/Unlit declarations in all passes, including the desktop passes. The built-in per-draw buffer also shares one declaration across Desktop and Mobile passes for SRP Batcher compatibility. Mobile HLSL does not include the desktop LightLoop or ShaderVariablesGlobal buffer. **Rendering → Batching → SRP Batcher** controls native compatible renderer submission using the HDRP asset setting; explicit Mobile Instance Groups can coexist with it. Standard GPU Instancing is supported; DOTS/BatchRendererGroup and rendering-layer light linking are not implemented in the mobile backend.

HDAdditionalLightData already converts authoring intensity to Light.intensity (lux for directional, candela for punctual lights). The mobile backend consumes VisibleLight.finalColor directly, including color temperature, and applies inverse-square punctual attenuation. It does not apply a second intensity/unit conversion. Fixed exposure uses Core's EV100 conversion. The metallic Lit BRDF follows URP 14.0.9; existing HDRP property packing and light units remain unchanged. See [URP material alignment](Mobile-URP14-Alignment.md) for input mapping, transparency migration and validation boundaries. Fog, color grading and bloom are not pixel-identical to full desktop HDRP or URP.

Post-processing effects use the standard HDRP Volume stack. Color grading parameter conversion (`ColorGradingUtilities.cs`) and shader implementation (`ColorGradingCommon.hlsl`) are shared with Desktop. Mobile builds a rasterized 2D strip LUT in RGBA16F, using the asset's LUT size, while Desktop retains its compute 3D LUT. Both use the same grading order, LogC/ACES spaces, curves, and None/Neutral/ACES (approximate or full)/Custom/External SDR tonemappers. Player rendering reuses the LUT when settings are unchanged; overridden curves and external LUT contents regenerate it. Edit-mode rendering and Frame Debugger replay rebuild it, and Editor first-use shader variants compile before the cache is marked valid. Neutral cameras bypass the LUT entirely to preserve ungraded HDR precision. This does not add HDR display output support.

Bloom retains three mobile downsample levels (half, quarter, eighth) and bilinear composition. It shares Desktop's quadratic soft threshold and gamma-to-linear threshold conversion, exponential intensity, and luminance-normalized tint. Scatter, dirt, anamorphism and high-quality Desktop reconstruction remain unsupported. FXAA is enabled only when the HDRP camera selects Fast Approximate Antialiasing. Scene View reads HDRP Scene View camera Anti-aliasing settings and respects the view's post-processing display toggle. Legacy Mobile Rendering/FXAA Volume values are ignored. Selecting unsupported SMAA/TAA does not implicitly select FXAA. The Postprocess master switch and individual Color Grading, Tonemapping, Bloom and Anti-aliasing Frame Settings are respected; reflection captures continue to bypass post-processing. Volume weights, masks, and camera anchors apply normally. Legacy asset Bloom/FXAA flags remain ignored.

Motion Blur, Depth of Field, TAA, lens distortion, chromatic aberration, vignette, film grain, dithering and custom post effects are not implemented by this mobile stack. The audit reports unsupported Volume components. These require separate mobile passes/resources; enabling a Desktop Volume does not silently initialize Desktop managers.

Mobile and Desktop share the standard **Exposure** Volume and the same fixed/physical parameter resolver. Use **Mode = Fixed**, **Fixed Exposure (EV100)** and **Compensation** in the same Volume Profile to author both paths; Physical Camera mode reads the same camera aperture/shutter/ISO. No separate Mobile EV parameter is needed. Mobile respects the global/camera **Exposure Control** Frame Setting, and Scene View inherits the main camera's Volume mask/anchor using the Desktop selection rules.

Exposure is applied before writing RGBA16F. Fixed EV, compensation, physical camera aperture/shutter/ISO and registered lens attenuation follow Desktop conversion. Unlit base color remains display-referred; emission respects Emissive Exposure Weight. Automatic exposure meters a 64/128/256 grid before post-processing and updates next-frame GPU history per camera. Histogram/Curve modes use lightweight Automatic; unsupported masks use Center Weighted. Fixed Exposure and Compensation initialize history without changing Desktop's serialized mode; this project's seed remains EV 10. See [Mobile production workflow](Mobile-Production.md) for settings, fallback details, baking and validation. Equal EV does not imply equal BRDF output.

When **Sky Fallback** is enabled and no explicit cubemap is assigned, Mobile resolves HDRI/Gradient from the camera's Volume stack, then approximates Physical Sky or falls back to `RenderSettings.skybox` (`Skybox/Cubemap` or `Skybox/Procedural`). HDRI rotation/intensity and Gradient colors are retained. Physical Sky becomes a sun-lit gradient with a sun disk; it does not reproduce atmospheric scattering, aerial perspective, clouds, backplates or distortion. Legacy URP skybox exposure is display-referred and retains the material's own exposure, independently of HDRP camera EV. Sky rendering does not generate lighting probes or realtime reflections; continue using baked environment lighting. Disable Sky Fallback for the original explicit-cubemap/clear behavior.

## Implementation and resource lifetime

Optional CPU instance culling/submission is documented in [Mobile Instances](Mobile-Instances.md). It uses explicit opt-in groups, conservative cell/AABB/distance/LOD culling and per-instance lighting, while retaining native shadow casters and renderer fallbacks.

`HDRenderPipelineAsset.rendererMode` selects the backend at construction. The Mobile branch precedes desktop API checks and all desktop initialization. It uses its own RenderGraph, VolumeStack and three raster materials. SkyManager, LightLoop resource containers and the desktop RenderGraph are constructed only in Desktop mode. Disposal releases the mobile graph/materials/VolumeStack and restores the global shader tag, keyword, lighting flags, SRP Batcher and rendering features.

The Forward graph records main-light and local-light shadows, forward opaque geometry, cubemap background, forward transparency, optional bloom and final grading/FXAA/output. It allocates RGBA16F color, depth, separate directional and local shadow atlases (each uses a 1×1 neutral allocation when unused), and optional bloom levels. Deferred adds the GBuffer and lighting stages described in [Mobile deferred](Mobile-Deferred.md). Automatic exposure maintains per-camera history; neither path allocates velocity buffers, screen-space pyramids or compute light lists. GPU memory varies with the output target, optional passes and RenderGraph pooling.

Built-in `ShadowCaster` and Editor picking/selection passes select the mobile implementation with `HDRP_MOBILE_RENDERER`. Their entry-point declarations remain outside keyword conditionals so Unity does not discard the mobile stage. Rendering uses `MobileForward`; desktop renderers continue selecting their existing LightModes. Desktop shared HLSL was extracted into include files without changing its definitions.

Build validation checks the included assets before desktop platform validation. Shader stripping preserves the union of the included renderer modes: mobile assets retain mobile raster passes and mobile ShadowCaster variants; desktop assets retain their own variants. User-owned compute shaders are not removed merely because the pipeline is Mobile. Assets referenced from scenes or included through HDRP's build label also participate. Dynamically loaded/addressable content must ensure its pipeline assets and shader variants are included in the application's build workflow.

## Benchmark and validation

**Rendering > HDRP Mobile > Create Benchmark Scene** generates a new Assets folder with a scene, Mobile asset, Volume profile, lighting settings, materials, a skinned mesh and deterministic cutout texture. It does not overwrite existing assets or automatically change Graphics/Quality settings. Save any untitled authoring scene when Unity asks, and open the benchmark scene by itself before running it.

Alternatively import **Mobile Renderer Benchmark** from this package's Samples. It includes a baked fixture; select its `Mobile.asset` for Graphics/Quality explicitly. The saved Volume uses fixed EV100 14 for the 100,000 lux sun. Re-bake after changing static geometry or lighting. Diagnostic unsupported-material drawing is disabled in this benchmark asset to keep its renderer scan out of performance measurements.

The fixture contains 36 static blocks, a ground receiver, one main light, four local lights, eight cutout cards, a transparent sphere, a two-bone animated capsule, a Light Probe grid and a baked Reflection Probe. Bake lightmaps using a Desktop asset with a supported Desktop build target selected (for example Windows), save the lighting data, then switch back to the Mobile asset. Cubemap Reflection Probes can be baked directly with Mobile active using HDRP's probe Inspector or `LightmappingHDRP.BakeProbe`; save the scene before an Inspector/Bake All bake. Do not use the legacy `Lightmapping.BakeReflectionProbe` API. Unbaked content is not a valid baked-lighting performance baseline.

HDRP Reflection Probes use a Mobile-owned RGBA16F 2D-array octahedral atlas (one GGX slice), with the same Core octahedral mapping, seam wrapping, mip padding and roughness-to-mip convention as Desktop HDRP. **Reflection Atlas Size** under Lighting controls 1024–4096 (default 2048, rounded up to a power of two). Up to 16 visible probes occupy a 4×4 tile grid. Higher importance wins capacity selection, then camera distance; equal-importance influences blend together. Atlas updates perform deterministic 64-sample raster GGX filtering and do not initialize the Desktop compute cache. The filter sample budget and fixed tile allocator differ from Desktop HDRP.

Both Forward and Deferred consume `HDAdditionalReflectionData.texture`, including Baked, Custom and existing Realtime cube textures. Rotated box/sphere influences, per-face box blend distances, probe weight/multiplier, range compression and box/sphere/infinite proxy projection are supported. Uncovered influence weight falls back to the runtime sky when Environment Lighting is enabled. Normal-dependent influence fading, light-layer masks, APV normalization and distance-based roughness are not implemented. Planar probes are not part of this cube atlas.

The editor chrome gizmo uses the current camera projection, exposure and scene depth in Mobile, so it follows the probe in world space instead of remaining fixed on screen. The Reflection Probe Inspector renders its sphere directly with the Mobile preview pass rather than a built-in preview camera. Drag to rotate; the Exposure and Mip controls adjust the preview independently of the Scene camera and do not change the baked texture.

Baked/Custom cache entries refresh when texture identity or HDRP texture hash changes. Existing Realtime cube textures refresh each camera render; Mobile still does not schedule realtime probe capture. Editor cubemap baking uses six Mobile Forward captures at the requested probe resolution, even when the asset uses Deferred or a reduced screen render scale. Captures retain linear HDR and probe range compression, bypass camera exposure and post-processing, and include only renderers/terrain marked Reflection Probe Static. They exclude local reflection feedback and do not implement iterative reflection bounces. Captured EXRs use HDRP's normal importer and baked texture binding, then enter the octahedral atlas automatically. Planar baking still requires Desktop HDRP. The existing baked-to-native texture bridge remains for native culling/legacy fallback and restores original bindings on disposal. Runtime lighting of visible HDRP probes samples the octahedral atlas, not the per-object cubemap pair.

The benchmark follows the same 30-second camera orbit and bone animation, warms up for 300 seconds and captures for 600 seconds. It saves JSON under `Application.persistentDataPath` with device/GPU/driver/OS, internal and output dimensions, sample counts and nearest-rank frame-time percentiles. CPU/GPU frame timing percentiles are recorded when FrameTimingManager supplies them; `-1` means unavailable, not zero. Enable Frame Timing Stats in Player settings for supported device timing queries. Temperature is an explicit operator observation field; no GPU temperature is fabricated from battery temperature.

Acceptance requires fixed 1920×1080 internal resolution at render scale 1 for the entire capture and P95 frame time ≤16.67 ms, after the full warmup and capture intervals. Gather separate reports for Adreno and Mali, including thermal conditions, and retain captures showing the actual pass list. No device coverage or frame-rate guarantee is implied by a successful compilation.

Automated checks:

- `MobileRenderTests` (EditMode): legacy defaults, platform gate, non-mutating content audit, percentile behavior and idempotent resource/global-state cleanup.
- `MobileURPMaterialTests` (EditMode, graphics device required): direct/indirect metallic BRDF and transparency source contributions compared on GPU against pinned URP 14.0.9 reference code.
- `MobileImageTests`, `MobileShadowTests`, `MobileExposureTests`, `MobileStabilityTests`: actual Forward/auxiliary passes, per-camera state, cascade sampling, desktop exposure reference, construction failures and repeated resource replacement.
- `UnityEditor.Rendering.HighDefinition.MobilePlayModeValidation.Run`: disposable batch project only; repeats PlayMode with and without domain reload and records errors/resource counts.
- `UnityEditor.Rendering.HighDefinition.MobileRenderValidation.Run`: batch entry point for a **disposable** Unity project; validates desktop/mobile shader passes and mobile feature variants, renders offscreen Unlit and Lit/shadow comparisons, and creates a benchmark fixture. PNGs are written alongside the temporary project's Assets folder. Do not run this entry point against an authoring project: it replaces the open scene and temporary Graphics/Quality settings.
- `UnityEditor.Rendering.HighDefinition.MobileRenderValidation.BuildAndroid`: batch entry point for the same disposable project with Android selected; builds an ARM64 IL2CPP Vulkan development APK. It intentionally configures that project's Player/Quality settings for the benchmark.
- `UnityEditor.Rendering.HighDefinition.MobileRenderValidation.ExportAndroid`: exports the same Gradle project without dependency download/packaging; this is useful for separating Unity compilation from Android build-tool/network failures.

Maintain separate mobile image baselines. Desktop render and existing HDRP tests must continue passing after changes to shared shader declarations or pipeline lifecycle code. Test domain reload, asset switching, scene switching, multiple cameras, RenderTextures, cutout/double-sided/transparency, skinned meshes, instancing, baked lightmaps/probes, cascade boundaries, missing resources and incompatible build assets. Mobile performance and thermal acceptance require physical devices.
